# Практикум по Kubernetes

Сквозной проект: один стек проходит все этапы. Порядок строгий, каждый этап закрывается приёмкой. Чужой YAML не копируется — каждый манифест пишется с нуля, и любое поле в нём объясняется. Сквозной вопрос ко всему практикуму: что в docker-compose делалось иначе или не делалось вовсе, и зачем Kubernetes так устроен.

## Приложение

Маленький стек:

- `api` — FastAPI или Flask, отдаёт JSON, ходит в Postgres и Redis
- `worker` — Celery или RQ, разбирает задачи из Redis
- `postgres` — база
- `redis` — брокер и кэш

Сначала собери его в `docker-compose.yml` и проверь, что работает. Это точка отсчёта «как было».

---

## Этап 0. Кластер и инструменты

Подними локальный кластер на `kind` или `minikube`. Поставь `kubectl`, настрой автодополнение и контекст.

**Приёмка:**
- `kubectl get nodes` показывает ноды в статусе Ready
- объяснить разницу между нодой, подом и контейнером
- запустить одноразовый под `kubectl run tmp --image=alpine -it --rm -- sh`, осмотреться, выйти

---

## Этап 1. Pod, ReplicaSet, Deployment — руками и по отдельности

Задеплой только `api`. Без Helm, голым YAML. Напиши три манифеста раздельно: сначала `Pod`, потом `ReplicaSet`, потом `Deployment`. Под каждым убей под через `kubectl delete pod` и посмотри, кто воскреснет, а кто нет.

**Приёмка:**
- `kubectl scale deployment api --replicas=3` поднимает три пода
- удаление одного пода тут же создаёт замену
- объяснить цепочку Deployment → ReplicaSet → Pod через labels

Пометь один под новым label через `kubectl label` так, чтобы он выпал из-под selector ReplicaSet. Что сделает контроллер и сколько подов останется?

---

## Этап 2. Service и связывание по сети

Опубликуй `api` через `Service` типа `ClusterIP`. Подними `postgres` и `redis` своими Deployment и Service. Перенастрой `api` ходить в базу по DNS-имени сервиса, не по IP.

**Приёмка:**
- `api` достучался до Postgres по имени сервиса, а не по IP
- `kubectl port-forward` открывает API в браузере
- объяснить, куда уйдёт трафик, если за Service стоят три пода
- знать разницу между ClusterIP, NodePort и LoadBalancer

---

## Этап 3. ConfigMap и Secret

Вынеси конфигурацию из манифестов. URL Redis и имя базы — в `ConfigMap`. Пароль Postgres и ключи — в `Secret`. Подключи их двумя способами: через `envFrom` и через volume-mount файлом.

**Приёмка:**
- в манифестах Deployment не осталось ни одного хардкоженного пароля
- смени значение в ConfigMap и объясни, подхватит ли его уже запущенный под; для env и для смонтированного файла ответ разный

---

## Этап 4. Probes и жизненный цикл

Добавь в `api` эндпоинты `/healthz` для liveness и `/readyz` для readiness — последний реально проверяет коннект к Postgres. Пропиши `livenessProbe`, `readinessProbe` и `startupProbe`. Выставь `resources.requests` и `resources.limits` по CPU и памяти.

**Приёмка:**
- сломай `/readyz` — под жив, но выпал из Service, трафик на него не идёт
- сломай `/healthz` — под перезапускается, это видно в `kubectl describe`
- поставь заведомо маленький лимит памяти, поймай `OOMKilled` и покажи его в статусе и событиях пода

---

## Этап 5. Хранилище для Postgres

Замени эфемерный Postgres на `StatefulSet` с `PersistentVolumeClaim`. Убедись, что данные переживают удаление пода.

**Приёмка:**
- записал строку в базу, удалил под Postgres, после перезапуска строка на месте
- объяснить, почему обычному Deployment с Postgres нельзя просто поставить `replicas: 3`

---

## Этап 6. Rolling update и откат

Выкати новую версию `api` сменой тега образа. Настрой стратегию `RollingUpdate` с `maxUnavailable` и `maxSurge`. Потом сломай выкат намеренно — подсунь битый образ — и откатись через `kubectl rollout undo`.

**Приёмка:**
- во время выката `api` отвечает без единой ошибки; проверь фоновым циклом `curl`
- битый образ не уронил прод, потому что readinessProbe не пустила трафик на сломанные поды
- `kubectl rollout undo` вернул рабочую версию, история видна в `rollout history`

---

## Этап 7. Ingress

Поставь ingress-controller на nginx. Заведи `Ingress`, чтобы `api` открывался по хосту `api.local` на пути `/api`. Пропиши хост в `/etc/hosts`.

**Приёмка:**
- `http://api.local/api` открывается без port-forward
- объяснить разницу между Service типа LoadBalancer и Ingress и зачем нужен роутинг по host и path

---

## Этап 8. Автоскейлинг

Включи `HorizontalPodAutoscaler` для `api` по CPU. Нагрузи сервис через `hey`, `ab` или простой цикл и поймай момент, когда поды начинают размножаться.

**Приёмка:**
- под нагрузкой `kubectl get hpa` показывает рост реплик
- объяснить, почему без `resources.requests` автоскейлинг по CPU не заведётся вовсе

---

## Этап 9. CI/CD из GitLab в кластер

Перепиши `.gitlab-ci.yml`: сборка образа, пуш в registry, деплой в кластер. Сначала прямой `kubectl apply` из пайплайна с kubeconfig в CI-переменных. Потом перепиши манифесты на Helm-чарт и деплой через `helm upgrade --install`.

**Приёмка:**
- пуш в `main` собирает образ и сам выкатывает его в кластер
- теги образа, число реплик и env вынесены в `values.yaml`, не зашиты в шаблоны
- объяснить, чем `helm upgrade` удобнее голого `kubectl apply` для версионирования релизов и откатов

---

## Этап 10. Боевые сценарии

Разбор без подсказок. Каждый случай — через `describe`, `logs` и `events`, с проговариванием хода мысли.

1. Под застрял в `Pending`. Найди причину: не хватает ресурсов ноды, не привязался PVC, не сошёлся nodeSelector.
2. Под в `CrashLoopBackOff`. Достань логи предыдущего запуска через `logs --previous` и найди, что его убивает.
3. `api` не видит Postgres. Пройди по цепочке: DNS, selector у Service, labels у подов, NetworkPolicy. Зайди внутрь пода через `exec` и проверь связь руками.
4. После выката половина запросов отдаёт 503. Объясни, как это связано с readinessProbe и `maxUnavailable`.
